# ADR-001: Use Layered Architecture

**Status:** Accepted

**Project:** Library Seat Reservation System

### 1. Context

The system must allow students to view seat availability, make and cancel reservations, and prevent double bookings. Library staff must be able to manage seat availability.

The architecture should be simple, maintainable, and suitable for a small team developing a semester project.

### 2. Decision

We decided to use Layered Architecture with a React frontend, Python FastAPI backend, and PostgreSQL database.

The backend will centralize business rules, including reservation validation and conflict prevention. The frontend will communicate with the backend through REST APIs.

### 3. Alternatives Considered

- **Layered Architecture:** Simple structure, clear separation of responsibilities, and easier testing.
- **Microservices Architecture:** Independent deployment and scaling, but greater complexity and operational overhead.

### 4. Consequences

**Positive:**
- Easier to develop and understand.
- Clear separation between UI, business logic, and data.
- Easier testing and maintenance.
- Appropriate for a small development team.

**Negative:**
- The backend is deployed as a single application.
- Independent scaling of individual backend features is limited.
- Changes to shared backend code may require redeploying the entire backend.

### 5. Conclusion

Layered Architecture provides an appropriate balance between simplicity, maintainability, and functionality for the Library Seat Reservation System.
